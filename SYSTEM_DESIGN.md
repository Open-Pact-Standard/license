# Open-Pact Standard — System Design (v1.3.1)

> **Audience:** Creators considering adopting OPL-1.3.1, commercial users evaluating compliance, and contributors who want to understand what's in scope.
>
> **One-sentence summary:** A fair-source license (free personal use, paid commercial use at the Maintainer's price) with optional steganographic fingerprinting for real enforcement. No chain, no system token, no DAO, no registry required. Adopt in under an hour.

## What's core (required to adopt OPL-1.3.1)

1. **LICENSE.md** — the license text. Copy to repo root.
2. **NOTICE file** — generated by `opl_init.py`. Contains Maintainer, jurisdiction, Standard Terms URL, OPL-AI opt-in/out.
3. **Standard Terms URL** — HTTPS HTML page. Pricing + payment mechanism + scope. The only external dependency.
4. **SPDX headers** — `SPDX-License-Identifier: OPL-1.3.1` in source files. Added by `opl_spdx_inject.py`.
5. **Package manifest reference** — `license: "OPL-1.3.1"` in package.json, Cargo.toml, pyproject.toml, etc.

## What's optional (adopt if you want, not required)

1. **Fingerprinting** — canary tokens + release fingerprinting + verifiable publication + evidence package. Real enforcement, but optional. Adopt if you want to protect against unauthorized commercial use with cryptographically verifiable evidence.
2. **x402 crypto payments** — `opl_x402.py` generates payment integration code. Optional. Stripe, bank wire, or email are the primary patterns.
3. **Structured fee schedule (REGISTRY.json)** — `opl_registry_gen.py` generates a structured fee schedule. Optional. Not required by the license.

## What's out of scope (separate products, not part of this license)

1. **On-chain Solidity framework** — `RoyaltyRegistry`, `LicenseIssuer`, `CanaryRegistry`, `GuildRoyalty`, reference DAO. These are OPL-1.1-era contracts. If they exist as a separate product, they have their own versioning and docs. They are not required by OPL-1.3.1.
2. **$OPL token** — no system token. No token economics.
3. **DAO / guild governance** — the Maintainer is the steward. No governance layer in the license.
4. **Enterprise SDK / SPDX identifier submission** — deferred.

## How adoption works (creator)

1. Copy `LICENSE.md` to repo root.
2. Run `python3 opl_init.py` → answers 6 questions → valid `NOTICE` file.
3. Run `python3 opl_spdx_inject.py .` → `SPDX-License-Identifier: OPL-1.3.1` on every source file.
4. Run `python3 opl_check.py .` → confirms setup is valid.
5. Write Standard Terms page (use `standard-terms.html` template or write your own). Host at the URL in NOTICE.
6. Reference `license: "OPL-1.3.1"` in your package manifest.

That's it. No registry. No chain. No token. No DAO. No framework.

## How compliance works (commercial user)

1. See `LICENSE.md` and `NOTICE` in the repo.
2. Read NOTICE → find the Standard Terms URL.
3. Go to the URL → read the pricing and payment mechanism.
4. Pay per the terms if you want to use the Work commercially.
5. If OPL-AI is opted in, don't use the Work for AI training/fine-tuning/distillation/etc. (unless you have a separate written agreement).

No on-chain verification. No guild registry. No token. No DAO.

## How enforcement works (if the creator opts in to fingerprinting)

1. Run the canary embedder → embed unique canary tokens in source (variable injection, dead code, watermark comments, string literals — steganographic, hidden in plain sight).
2. Build Merkle tree from canary secrets → publish only the Merkle root.
3. Fingerprint the release → SHA3-256 of distribution archive + unique textual fingerprint.
4. Publish Merkle root + fingerprint in a GPG-signed Git tag (or release notes). This is the verifiable, timestamped publication.
5. Keep canary secrets + full manifest offline (for litigation).
6. If a canary is found in suspect code: reveal the canary secret + Merkle proof → proof that the suspect code derives from the Maintainer's distribution. The evidence package (assembled by the tooling) is litigation-ready.

**What fingerprinting proves:** that the suspect code contains canaries from the Maintainer's distribution → the suspect code derives from the Maintainer's Work.

**What fingerprinting doesn't prove:** that the suspect code was used for AI training (unless the canary is found in the training data or model outputs), that paraphrase or distillation occurred, that the Maintainer's specific pricing was violated (that's the Standard Terms URL's job).

**Honest enforcement reality:** canary tokens detect verbatim source inclusion. They don't detect paraphrase, distillation, or stripped canaries. Release fingerprinting identifies which distribution leaked. The evidence package is real and verifiable, but it's evidence, not a substitute for legal process. This is an honest, real enforcement layer — not an empty threat.

## Version policy

- **One version for the core system:** OPL-1.3.1. The license text, the tools, the NOTICE format, the Standard Terms URL convention, the OPL-AI addendum — all v1.3.1.
- **The fingerprinting tooling** (canary embedder, release fingerprinter, evidence package) is part of the core system, versioned with it.
- **The on-chain Solidity framework** (if it exists) is a separate product with its own versioning. OPL-1.3.1 does not depend on it.
- **v1.4 and later** will be new versions with new version numbers, not retroactive changes to v1.3.1. Existing NOTICE files and Standard Terms URLs continue under the version they adopted.
